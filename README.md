# ПОС — преподавательская оценка студентов

Домашнее задание №2 по КПО. Консольное приложение на C# и .NET 10.

## О проекте

Я сделал небольшую систему для учёта оценок студентов. 
В программе можно добавить студентов, составить рубрикатор, выставить оценки и получить итоговый балл. У каждого критерия есть максимальный балл и вес, поэтому итог считается не просто как сумма оценок, а с учётом их вклада в общий результат. Также можно посмотреть текущий результат по уже оценённым критериям и выгрузить итоговую ведомость в CSV.

## Что умеет программа

Через консольное меню можно:

- добавлять студентов и смотреть их список;
- создавать критерии оценивания с названием, максимальным баллом и весом;
- выставлять студентам оценки по выбранным критериям;
- смотреть, исправлять и отменять выставленные оценки;
- рассчитывать итоговый балл и текущий результат;
- сохранять итоговую ведомость в CSV.

Основные ограничения проверяются не только при вводе, но и внутри доменной модели. Например, нельзя поставить отрицательный балл или больше максимума критерия, оценить несуществующего студента либо использовать критерий, которого нет в рубрикаторе. Повторно выставить оценку для той же пары «студент — критерий» тоже нельзя: её нужно исправить отдельной командой.

Итоговая оценка нигде не хранится как отдельное число. Она каждый раз рассчитывается заново по актуальным оценкам и критериям, поэтому исправление или отмена оценки сразу влияет на результат.

## Как запустить

Для запуска нужен .NET 10 SDK. Я работал на Mac через VS Code. В терминале из корневой папки проекта нужно выполнить:

```bash
dotnet restore POS.slnx
dotnet build POS.slnx
dotnet run --project POS.Console
```

После запуска откроется меню, в котором можно вручную добавлять студентов, критерии и оценки.

Есть также подготовленный сценарий для быстрой проверки программы:

```bash
dotnet run --project POS.Console < examples/demo-input.txt
```

Для запуска тестов:

```bash
dotnet test POS.slnx
```

## Как устроен проект

Я использовал облегчённую Clean Architecture и разделил решение на пять проектов:

- `POS.Domain` — доменная модель, ограничения и расчёт результатов.
- `POS.Application` — основные сценарии работы с ведомостью и интерфейсы для хранения и экспорта.
- `POS.Infrastructure` — хранение ведомости в памяти и запись CSV.
- `POS.Console` — меню, ввод и вывод, настройка зависимостей.
- `POS.Tests` — тесты модели, расчётов, сценариев и экспорта.

Зависимости направлены к внутренним слоям: `POS.Application` зависит от `POS.Domain`, а `POS.Infrastructure` реализует интерфейсы из `POS.Application`. При этом сам домен не зависит от консоли и способа хранения данных.

Консоль работает через `PosFacade`, который объединяет основные сценарии приложения. Зависимости настраиваются в `Program.cs` через DI-контейнер.

## Доменная модель и DDD

В проекте я использовал понятия из предметной области: `Student` — студент, `Criterion` — критерий, `Evaluation` — оценка, `Gradebook` — ведомость. Набор критериев образует рубрикатор. Эти названия используются и в коде, и при описании работы программы (Ubiquitous Language).

`Student` и `Criterion` — сущности (Entity), так как у них есть собственные идентификаторы. `Score` и `Evaluation` — объекты-значения (Value Object). `Score` хранит балл, а `Evaluation` связывает студента, критерий и полученную оценку. При исправлении оценки создаётся новое значение.

Корнем агрегата я выбрал `Gradebook`. Через него добавляются студенты и критерии, выставляются и изменяются оценки. Здесь же проверяются основные инварианты: нельзя поставить балл выше максимума, оценить несуществующего студента или использовать критерий, которого нет в рубрикаторе. Также нельзя повторно выставить оценку по одной и той же паре студента и критерия.

Для хранения ведомости используется интерфейс `IGradebookRepository` из Application. Его реализация `InMemoryGradebookRepository` находится в Infrastructure, поэтому домен не зависит от способа хранения данных.

Расчёт итоговой оценки вынесен в отдельный Domain Service — `FinalScoreCalculator`. Он вычисляет результат на основе оценок и весов критериев, а не хранит его как отдельное свойство студента.

## Как применены паттерны GoF

Для задания я выбрал три решения из разных групп паттернов. Старался использовать их там, где они упрощают реальную логику программы, а не добавлять классы ради количества.

### Factory — создание оценки

В `Evaluation` есть статический фабричный метод `Create`, а конструктор закрыт. Через этот метод создаётся оценка с проверкой допустимого балла. `Gradebook` сначала находит существующих студента и критерий, а затем передаёт их при создании оценки.

Так нельзя произвольно создать оценку с баллом выше максимума критерия. Это фабричный способ создания объекта с проверкой инвариантов. При этом здесь именно статическая фабрика, а не классический вариант GoF Factory Method с отдельной иерархией создателей.

### Facade — работа со сценариями

`PosFacade` находится в Application и служит общей точкой входа для консольного меню. Через него программа добавляет студентов и критерии, работает с оценками, получает рассчитанные результаты и подготавливает данные для экспорта.

Я использовал фасад, чтобы `ConsoleMenu` не обращался самостоятельно к репозиторию, калькулятору и экспортеру. Меню отвечает за общение с пользователем, а последовательность действий внутри сценариев остаётся в Application.

### Strategy — два способа расчёта

Для расчётов есть общий интерфейс `IFinalScoreStrategy` и две реализации:

- `AllCriteriaStrategy` учитывает весь рубрикатор. Если оценка по критерию ещё не выставлена, её вклад равен нулю.
- `EvaluatedCriteriaStrategy` учитывает только критерии, по которым оценка уже есть.

`FinalScoreCalculator` использует переданную стратегию и одну общую формулу. Поэтому два режима не требуют дублировать сам алгоритм расчёта. Выставленный ноль при этом не считается пропущенной оценкой и учитывается в обоих вариантах.

## Как считается результат

Итоговая оценка рассчитывается по десятибалльной шкале с учётом веса каждого критерия. Для этого балл делится на максимум критерия, умножается на его вес, а полученные значения суммируются и делятся на общую сумму весов.

Например, если за проект студент получил 8 из 10 с весом 3, а за тест — 4 из 5 с весом 1:

```text
10 × ((8 / 10) × 3 + (4 / 5) × 1) / (3 + 1) = 8,00
```

В программе есть два варианта расчёта. Итоговая оценка учитывает все критерии, даже если по некоторым ещё нет оценок. Текущий результат учитывает только уже оценённые критерии.

Для вычислений используется `decimal`, результат округляется до двух знаков после запятой. Если учитывать нечего, программа возвращает 0,00.

## Экспорт и тестирование

Для экспорта используется интерфейс `IGradebookExporter` и его реализация `CsvGradebookExporter`. В CSV сохраняются ID студента, его имя и итоговая оценка. Файл записывается в UTF-8, специальные символы обрабатываются корректно.

Для тестирования я использовал xUnit. Тесты проверяют ограничения доменной модели, расчёт оценок, работу `PosFacade` и экспорт CSV.

Я собрал проект на своём Mac и запустил тесты — все 22 прошли успешно. Также проверил демонстрационный сценарий и содержимое `vedomost.csv`. После исправления оценки результат Анны Ивановой изменился с 8,00 до 9,13, а итог Бориса Петрова составил 5,63. Все значения корректно сохранились в CSV.
